# Leakage checks

Each way information from the future, or from the answer itself, could leak into a model, and
how it is prevented and verified. Started in Phase 3; Phase 4/5 rows are completed when those
phases run.

| # | Risk | Prevention | Verified by | Status |
|---|---|---|---|---|
| 1 | Consumption lag/rolling features include the target day or later days | Every feature built from `shift(k)` with k ≥ 1; rolling windows applied to the series shifted by 1 day | `test_consumption_features_never_use_target_day_or_future`: multiplies the target day and all later days by 100 and asserts the features for that day are unchanged | ✅ passes |
| 2 | Wrong lag definition (off by one) | Features indexed by target day; `lag_k` = consumption k days before it | `test_lag_definitions` checks `lag_1`, `lag_7` and `roll_mean_7` against hand-computed values | ✅ passes |
| 3 | Solar features derived from the output (DAILY_YIELD, TOTAL_YIELD, DC_POWER, interval energy) | `FORBIDDEN` set in `features/solar.py`; `check_no_leakage` runs every time features are built | `test_solar_features_exclude_output_derived_columns` (including that a forbidden column raises an error) | ✅ passes |
| 4 | Shuffled train/test split mixes future and past | Consumption split by date (train ≤ 2008-12-31, valid 2009, test 2010); solar split by whole calendar days (24 / 5 / 5) | `test_splits_are_chronological_and_disjoint` | ✅ passes |
| 5 | 15-minute rows of the same day in both train and test (near-duplicate neighbours) | Solar split assigns whole days, never individual rows | same test (split works on unique dates) | ✅ passes |
| 6 | Scaler/encoder fitted on all data | StandardScaler and OneHotEncoder only inside `make_pipeline`, fitted with the model on training rows | code structure (`features/preprocess.py`); Phase 4 fits pipelines on the training split only | ✅ in place |
| 7 | Holiday or calendar features "know" something unknowable | Calendar facts about the target day (weekday, month, public holiday) are known in advance, so they are legitimate | design review | ✅ |
| 7b | Weather features use the target day's observed temperature (unknown when forecasting the evening before) | Main features use past temperature only (`t2m_lag_1`, `t2m_mean_3d`, `hdd_lag_1`, `hdd_sum_7d`); target-day temperature is kept in `FORECAST_PROXY_FEATURES`, outside `FEATURES`, for a labelled experiment only | same leakage test now also perturbs the weather columns and asserts the proxy features are not in `FEATURES` | ✅ passes |
| 7c | India (eMARC): a meter's features use its own future, or another household's data | Features built per meter (`groupby(deployment_id)`), all history/load-shape/weather features shifted ≥ 1 day; meters are never summed | `test_india_features_use_only_the_past_and_only_the_same_meter`: scales the meter's own future and a *different* meter's whole series ×10 and asserts the features for that day are unchanged | ✅ passes |
| 7d | India: interpolated values scored as if measured | Interpolated days are dropped as targets (`finalize`), allowed only inside lag features | `test_india_finalize_drops_interpolated_targets_and_labels_lockdown` | ✅ passes |
| 7e | India: split by date leaks across meters (e.g. meter A's 2020 days in train) | One calendar split for every meter (train ≤ 2019-06-30 < valid ≤ 2019-12-31 < test); lockdown days labelled and reported separately | same test (`split`, `period` labels) | ✅ passes |
| 8 | Hyperparameter tuning peeks at validation/test data | Expanding-window CV over whole days *inside* the training period only (`models.common.day_cv_splits`) | Solar 4B: folds checked (no shared days, train always earlier). Consumption 4A: same day-based folds on the training split only (India 4 folds, France 5), per-fold MAE stored in `consumption_*_tuning.json`; quantile and forecast-proxy models reuse the tuned settings, fitted on training rows only | ✅ |
| 11b | Healthy-reference label (built from actual output) leaks into the model | Used only to choose training rows and an evaluation subset; not in `FEATURES` | `check_no_leakage` + `test_training_rows_are_train_daytime_eligible_and_healthy` | ✅ |
| 9 | Test set used more than once | Test metrics computed once, in Phase 5, after the model is chosen on validation; the run records the SHA-256 of every model file and refuses a later run with different files (`models/evaluation.py`, `reports/metrics/test_run_log.json`) | `test_changed_model_after_test_run_is_refused`; Phase 5 re-runs (figure fixes) used identical model files; selection unchanged although Random Forest scored lower test MAE than the selected model for France and solar | ✅ |
| 9b | Interval calibration tuned on the test set | Conformal adjustment computed on validation only and stored in the model before the test run | `test_conformal_adjustment_reaches_target_coverage_and_widens_interval`; test coverage reported separately | ✅ |
| 9c | Monitoring thresholds chosen while looking at the solar test days | Disclosed, not prevented: the 4C monitoring window (22 May – 17 Jun) includes the 5 solar test days, and `peer_max_pr` was set after looking at Plant 1 flags over that window. The expected-output model itself never saw test days; monitoring has no test claim of its own (it is checked with simulated faults) | design review | ⚠️ disclosed |
| 9d | India test split scored twice | Disclosed: after Phase 5 the India model was changed on validation evidence only (Phase 8: ensemble with members fixed in advance, refit on train + validation) and, with the owner's approval, the test split was scored again. The Phase 5 log, report and model were archived in `reports/archive_phase5/` and `models/archive_phase5/`, not deleted; both results are reported. Solar and France files are unchanged (same hashes). The second India number may be slightly optimistic | `reports/evaluation_report.md` banner; `_phase5_line` comparison | ⚠️ disclosed |
| 10 | Performance monitoring scores a day with a model trained on that day | Expanding window: the model for day d is refitted on days < d only (7-day warm-up) | `test_expected_output_uses_only_earlier_days` (later faulty days never enter the fit) | ✅ |
| 11 | Night rows inflate solar R² | Metrics reported on daytime rows (irradiation > 0) and on daily kWh | `models.solar.evaluate`, `test_daily_evaluation_sums_intervals_to_kwh` | ✅ |
| 12 | Weather model sees the future | Rows split by target date (train ≤ 2018, validation 2019–2021, test 2022–2025); a row whose origin and target fall in different splits is dropped; normals (climatology) come from the training years only; choice made on validation, test scored once with the final model refitted on 2001–2021 | `weather._split`, `reports/weather_model_report.md` | ✅ |
| 13 | Home-solar parameters fitted on test days | k, a, b fitted on the 24 Kaggle train days; daily check on the 5 validation days. Disclosed: one exploratory run printed the error of the a/b translation on the 5 test days (0.019 kW/m², 0.2 °C); nothing was changed after it and those numbers are not reported as results | `pv_home.fit` excludes `split == "test"` | ⚠️ disclosed |
| 14 | Simple home-use model scored on the eMARC test split a third time | Not scored on test at all: choice, 7-day error and the per-horizon blend weights come from validation (models fitted on train only); the blend weights are chosen on the same validation days, so the "used" 7-day error is slightly optimistic | `reports/home_use_simple_report.md` | ⚠️ disclosed |
